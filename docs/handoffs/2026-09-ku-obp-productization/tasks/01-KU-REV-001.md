## Objective

Determine which KU semantics are authoritative now and identify legacy claims
that conflict with the frozen vNext foundation before product code changes.

- `../README.md`, `../DECISIONS.md`, `../PROGRESS.md`
- `../../../PROJECT_STATUS.vi.md`

Use the Research Baseline's normative precedence and read its full relevant
sections if a conflict cannot be resolved from the vNext contracts. Do not load
unrelated OBT, BCI or mobile material.

## Deliverable

Create `../outputs/KU_AUTHORITY_AUDIT.md` containing:

- document authority table;
- canonical KU identity, ownership, lifecycle and storage statements;
- legacy-to-vNext terminology/meaning map;
- exact contradictions with file/section references;
- decision-required items separated from resolvable documentation drift;
- proposed scope for `KU-CON-001`, without inventing new behavior.

## Acceptance

- Every conclusion cites an authoritative source or is marked an open question.
- `encode ≠ publish`, `proposal ≠ materialize`, and `materialize ≠ adopt` remain explicit.
- No legacy `FULL`, consensus, popularity, PoMV or OBT state becomes KU truth/authority.
- No source or application code changes.
- `python scripts/ci/validate_vnext_contracts.py` and `git diff --check` pass.
- Update `../PROGRESS.md`; advance the README pointer only after owner-approved merge.

## Excluded

Implementation, API design, UI design, migration execution and networking.
